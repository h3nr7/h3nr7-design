Kubernetes in one line

Declare the state you want; the cluster keeps making it true.

A spec is a record of intent, not a script that runs once.

Controllers compare desired with actual, and close the gap.

Labels join Services to Pods, so Pods can come and go.

01 · The picture

Two paths meet at the Pods

A spec goes in on the left and becomes running containers; a request comes in on the right and is routed to one of them.

02 · Seven steps

Seven steps turn a YAML file into a running app

The steps are ByteByteGo's. Under each is the detail the official docs add, and one correction.

01

Describe the desired state

You write a deployment.yaml: which image, how many replicas, which labels. It says what should exist, not how to get there.

An engineer, a CI job or a GitOps tool can be the one that applies it.

02

The API server validates and stores it

The desired state goes into etcd, the persistent store for every Kubernetes resource: replica counts, existing Pods and nodes, and their assignments.

Only the API server talks to etcd. Components

03

Controllers close the gap

The controller manager runs loops that compare desired with actual. A Deployment asking for four replicas gets a ReplicaSet, and the ReplicaSet gets four Pods.

If a Pod dies later, the same loop replaces it. Deployments

04

The scheduler picks a node

Filtering removes nodes that cannot run the Pod: too little free CPU or memory, a placement rule. Scoring ranks the rest and the highest score wins.

It works from resource requests, not live usage. Scheduler

05

Worker nodes run the Pods

The kubelet sees the Pods bound to its node and asks the container runtime to pull the image and start the containers, then keeps checking them.

A correction: the kubelet does not track assignments. The scheduler records each binding through the API server. Architecture

06

A Service gives them one address

Pods are disposable and get a new IP each time. A Service is a stable name and virtual IP in front of every Pod whose labels match.

Only Pods passing their readiness probe receive traffic. Service

07

Ingress or Gateway lets users in

A default Service is reachable only inside the cluster. An Ingress or Gateway is the HTTP(S) entry that maps a hostname and path to it.

Ingress is frozen; Gateway API is recommended for new work. Ingress

03 · Who talks to whom

Every arrow starts or ends at the API server

Nobody calls anybody directly: components write to the API server and watch it for work.

04 · Components

Eight components, and what breaks without each

Four decide on the control plane, three do the work on every node, and one talks to the cloud.

ComponentLives onJobIf it is down
kube-apiserverControl planeExposes the Kubernetes HTTP API; the front door for kubectl, CI and every other componentNo changes or reads; running Pods keep running
etcdControl planeConsistent, highly available key-value store for all cluster dataCluster state is unavailable. Back it up
kube-schedulerControl planeFinds Pods with no node and picks a suitable node for eachNew Pods stay Pending
kube-controller-managerControl planeRuns the control loops: Deployment, Node, Job, EndpointSlice and othersNothing self-heals or scales
cloud-controller-managerControl planeOptional. Links the cluster to the cloud provider: load balancers, routes, node checksNo new cloud load balancers
kubeletEvery nodeAgent that makes sure the containers of each Pod on its node are runningThat node's Pods are no longer managed
Container runtimeEvery nodePulls images and runs containers, for example containerd or CRI-ONo containers start on that node
kube-proxyEvery nodeOptional. Maintains the network rules that send a Service's virtual IP to one of its PodsService routing on that node goes stale

Production control planes usually run across several machines. Managed services (EKS, GKE, AKS) run the control plane for you. kube-proxy is optional because some network plugins do Service routing themselves.

05 · Objects

You create owners and addresses, rarely Pods

A workload object owns the Pods, and a Service gives them an address.

Workloads

ObjectUse it forBehaviour
PodThe smallest deployable unit: one or more containers sharing network and storageDisposable; a replacement gets a new IP
DeploymentStateless apps where any Pod is interchangeableManages ReplicaSets; rolling updates and rollback
StatefulSetApps needing stable identity or per-Pod storageSticky names (db-0, db-1), ordered rollout
DaemonSetOne Pod per node: log shippers, monitoring, network pluginsA new node gets its Pod automatically
JobA task that runs to completion onceRetries until it succeeds
CronJobA Job on a schedule: backups, reportsOne crontab line; make the task idempotent

Networking

ObjectUse it forBehaviour
Service · ClusterIPA stable in-cluster address for a set of Pods; the default typeReachable only inside the cluster
Service · NodePortThe same port opened on every nodePort range 30000–32767 by default
Service · LoadBalancerAn external load balancer from the cloud providerBuilds on NodePort
IngressHTTP(S) routing by host and pathStable, supported, but frozen: no new features
Gateway APIGateway and HTTPRoute: the successor to Ingress, with richer routing and a split between platform and app teamsRecommended for new work
Ingress is not being removed, but the community Ingress NGINX controller was retired and the project advises moving to Gateway API or another controller. The Ingress2Gateway 1.0 tool translates existing manifests.

Configuration, storage and organisation

06 · Manifests

Three manifests reproduce the diagram

The checkout app, end to end. The image name, hostname and ports are placeholders.

Deployment

The desired state from step 1.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout
spec:
  replicas: 4
  selector:
    matchLabels:
      app: checkout
  template:
    metadata:
      labels:
        app: checkout     # the Service matches this
    spec:
      containers:
        - name: checkout
          image: registry.example.com/checkout:v2
          ports:
            - containerPort: 8080
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { memory: 256Mi }
          readinessProbe:   # gate traffic until ready
            httpGet: { path: /ready, port: 8080 }
            periodSeconds: 5
          livenessProbe:    # restart if it hangs
            httpGet: { path: /healthz, port: 8080 }
            periodSeconds: 10

Service

The stable endpoint from step 6.

apiVersion: v1
kind: Service
metadata:
  name: checkout
spec:
  type: ClusterIP
  selector:
    app: checkout
  ports:
    - port: 80          # the Service listens here
      targetPort: 8080  # the container listens here

HTTPRoute

The entry point from step 7, attached to a Gateway your platform team or cloud supplies.

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: checkout
spec:
  parentRefs:
    - name: shared-gateway
  hostnames:
    - shop.example.com
  rules:
    - matches:
        - path: { type: PathPrefix, value: /checkout }
      backendRefs:
        - name: checkout
          port: 80

Day two on the same app

# Ship v3 with a rolling update, then watch it
kubectl set image deployment/checkout checkout=registry.example.com/checkout:v3
kubectl rollout status deployment/checkout

# v3 is broken: go back to the previous revision
kubectl rollout undo deployment/checkout

# A sale is on: scale by hand, or let an autoscaler do it
kubectl scale deployment/checkout --replicas=10
kubectl autoscale deployment/checkout --min=4 --max=20

A rollout starts only when the Pod template changes; scaling alone does not create a revision. By default a rolling update keeps at most 25% of Pods unavailable and adds at most 25% extra, and ten old ReplicaSets are kept for rollback.

07 · kubectl

kubectl is one pattern: verb, resource, name

The pattern is always kubectl <verb> <resource> [name] [flags]. Add -n <namespace> to pick a namespace and -o yaml or -o wide to change the output.

Look

kubectl get pods -o wide
kubectl get deploy,svc,pods -l app=checkout
kubectl get pods -A
kubectl describe pod <pod>
kubectl get events --sort-by=.metadata.creationTimestamp
kubectl top pods

Change

kubectl apply -f app.yaml
kubectl diff -f app.yaml
kubectl delete -f app.yaml
kubectl scale deployment/checkout --replicas=6
kubectl rollout history deployment/checkout
kubectl rollout undo deployment/checkout --to-revision=2
kubectl rollout restart deployment/checkout

Debug

kubectl logs <pod> -f
kubectl logs <pod> --previous
kubectl exec -it <pod> -- sh
kubectl port-forward svc/checkout 8080:80
kubectl get endpointslices \
  -l kubernetes.io/service-name=checkout
kubectl debug -it <pod> --image=busybox

describe pod is the first stop when a Pod misbehaves: the events at the bottom usually say why. logs --previous shows the container that just crashed.

08 · When to use it

It earns its keep with many services, not one

Kubernetes pays off when you run many containerised services that must stay up, scale and ship often. It is overhead for one small app. The capabilities are the ones the official overview lists; the judgement on fit is mine.

A good fit

  • Many services calling each other. Service discovery means checkout calls payments by name, not IP.
  • Frequent releases, no downtime. Rolling updates, and one command to undo.
  • Spiky traffic. Four replicas overnight, twenty during a sale.
  • Things that must survive a dead node. Its Pods are recreated elsewhere.
  • Mixed workloads on shared hardware. APIs, Jobs and CronJobs packed onto one node pool from their requests.
  • One model across clouds. The same YAML on EKS, GKE, AKS or bare metal.

Think twice

  • One or two small services. A PaaS, Cloud Run, ECS/Fargate or a single VM is less to look after.
  • Functions that sit idle. You pay for and manage idle nodes; serverless fits better.
  • Nobody to own the platform. Upgrades, networking and security need steady attention. At least use a managed control plane.
  • An app that is not containerised. Containerise it first, or leave it on VMs.
  • Your primary database, with no operator experience. Possible, but a managed database is the safer start.

Kubernetes is not an all-inclusive PaaS. It does not build your code or supply CI/CD, it ships no databases, message buses or caches, and it does not dictate logging, monitoring or alerting. You bring those.

09 · Habits

Eleven habits prevent most outages

Each one comes from the Kubernetes docs or the project blog; the links are in the references.

DoWhy
Set CPU and memory requestsThe scheduler places Pods by requests. Start modest (100m CPU, 128Mi) and tune from real usage
Set a memory limitWithout one a container can take all the memory on its node
Add a readiness probeTraffic reaches a Pod only once the probe passes
Add a simple liveness probeThe kubelet restarts a hung container; clever checks cause needless restarts
Use a startup probe for slow startersIt holds off the other probes until the app has booted
Never run naked PodsA bare Pod is not recreated if its node fails
Keep manifests in GitEvery change is reviewable and reversible
Label consistentlySelectors, queries and clean-up all depend on labels
Pin image tagscheckout:v2, not latest: a rollback needs to know what ran
A namespace per team, with a quotaIt stops one team starving another
Prefer Gateway API for new routingIngress is frozen; new features land in Gateway API

Three mistakes behind most first-week outages

  1. Selector and label mismatch. The Service selects app=checkout, the Pods say app=check-out. The Service exists and routes nowhere.
  2. No readiness probe. Pods take traffic while still booting, so every deploy produces a burst of errors.
  3. port and targetPort swapped. port is what the Service listens on, targetPort what the container listens on.

Conclusion

Four ideas explain most of Kubernetes

01

The spec is the record

What you applied is what the cluster keeps working towards.

02

Loops, not scripts

Controllers never finish; they compare and correct, for as long as the object exists.

03

Labels are the glue

Services and controllers find Pods by label, so a Pod is always replaceable.

04

One door

Everything reads and writes through the API server, which alone talks to etcd.

Delete a Pod and nothing is wrong, only briefly smaller.
